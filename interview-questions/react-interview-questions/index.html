React Interview Questions

React is an open-source frontend JavaScript library for building web interface/components.

Beginner

Section titled “Beginner”

1. What is Virtual DOM?

Section titled “1. What is Virtual DOM?”

A Virtual DOM is an in-memory representation of actual DOM. Its used in React to efficiently compare the DOM changes and applies the diff to the actual DOM. It basically improves the performance of rendering process as directly manipulating actual DOM would be slower and expensive.

2. What is JSX?

Section titled “2. What is JSX?”

JSX stands for JavaScript XML. Its a syntax extension for JavaScript that lets you write HTML like code directly inside your JavaScript files.

Tools like Babel or SWC convert JSX into standard JavaScript function calls (React.createElement()) before the code runs in a browser.

3. Difference between class component and functional component?

Section titled “3. Difference between class component and functional component?”

Class Components are es6 classes that extends React.Component and requires a render() function to return JSX. It rely on life cycle methods like componentDidMount(), componentDidUpdate() etc and manage state with this.state.

Functional Components are just general functions that takes props as input and return JSX. They rely on hooks (useEffect, useState, etc.) to handle life cycle events and manage state.

Functional component are preferred over class components as they are more cleaner and easier to understand. Class components are outdated but useful for error handling and can be used to create a ErrorBoundary component.

4. Stateless vs Stateful components

Section titled “4. Stateless vs Stateful components”

Stateless Components are often called as Presentational Components. They don’t manage state on their own. Instead they receive data via props and use them while rendering the component.

On the other hand A Stateful Component manages their state internally. They can update their state based on some user actions or events.

5. How to implement type checking in React?

Section titled “5. How to implement type checking in React?”

We can implement type checking at two different stages. At compile time using TypeScript and at run time using PropTypes(mostly with JavaScript).

But as of React 19, PropTypes are deprecated and its recommended to use TypeScript as standard.

6. What is the use of key prop?

Section titled “6. What is the use of key prop?”

The primary purpose of the key prop in React is to give each element or component instance a stable, unique identity across renders. This identifier tells React’s reconciliation engine exactly which item in the list have been changed/added/removed, allowing React to optimize performance and preserve component state accurately.

Without key, React defaults to matching items by their array index. If you add a new item at the top of the list, React thinks all the items in the list have been changed, causing it to unnecessarily re-render the entire list.

By using an unique key, React compares old key with the new key and realizes that the existing items simply moved down and only mounts the single new item. This significantly improves the rendering performance.

We should not use index as keys as indexes will change when length of the list changes. This will result similar to using components without key.

7. Controlled vs Uncontrolled component

Section titled “7. Controlled vs Uncontrolled component”

In controlled component form data is managed by component state but in Uncontrolled component, form data is managed by the browser DOM.

Feature Controlled Components Uncontrolled Components
Source of Truth React State (useState) The Browser DOM
Data Retrieval Accessed instantly via the state variable Pulled on demand using React Refs (useRef) or FormData
Value Tracking Updates continuously via an onChange handler Tracks internally; uses defaultValue for initial seeding
Re-renders Re-renders the component on every keystroke Does not trigger re-renders as the user types
Use Case Complex validation, dynamic layouts, and instant UI feedback Simple forms, non-React library integrations, and file uploads (<input type="file">)

8. How to share data between React components?

Section titled “8. How to share data between React components?”

In React, sharing data between components depends on the relationship between those components. The three primary approaches are passing data via Props, Lifting State Up and using the Context API.

  1. Parent to Child(Using Props)

    The most straightforward way to pass data is downward(unidirectional data flow) from a parent component to a child component using props.

  2. Child to Parent(Using Callback Functions)

    To send data up from a child to a parent, you still use props, but you pass a callback function from the parent to the child.

  3. Between Sibling Components(Lifting State Up)

    When two sibling components need to share the same changing data, you must lift the state up to their closest common parent component.

9. Explain state change cycle in react.

Section titled “9. Explain state change cycle in react.”

In React, the state change cycle describes the exact sequence of events that occurs from the moment a state variable is modified to the moment the updated user interface (UI) is painted on the screen.

Modern React operates this cycle via a internal framework paradigm called Render and Commit, which divides the cycle into three main phases: Triggering, Rendering, and Committing.

  1. Triggering a Render The cycle begins when a component’s state needs to change. This is usually sparked by user interactions (like clicking a button), network responses, or timers and a state updater function (like setCount from the useState hook) or this.setState() is called. Calling this function signals to React that the component’s UI is now out-of-date and needs to be recalculated. React queues this update.

  2. Rendering the Component Rendering means React is calling your component function to figure out what the UI should look like. React executes the component function from top to bottom using the new state values that returns a new tree of JSX elements(the Virtual DOM). For a state update, React compares this new JSX tree with the old tree from the previous render. It calculates exactly what changed.

  3. Committing to the DOM Once React knows exactly what changed, it enters the commit phase and updates the actual browser DOM. Because of the diffing process in the rendering phase, React only changes the specific DOM nodes that actually need updating. If your state update didn’t change what the JSX outputs, React won’t touch the DOM at all.

Once the DOM is updated, React releases control back to the browser. The browser repaints the screen, and the user finally sees the updated state reflected visually.

10. What is props mirroring?

Section titled “10. What is props mirroring?”

Props mirroring in React is an anti-pattern where a component copies an incoming prop directly into its own local state via useState or a constructor, leading to synchronized state issues.

Problem:

When you copy a prop straight into state upon initial render, the local state does not automatically update if the parent component changes that prop later on. This breaks the single source of truth principle in React.

Exception:

Sometimes developers want to initialize state from a prop. If you truly only need the initial value and will never sync it again, it is better to name the prop clearly (like initialValue or defaultCount) to signal that subsequent updates are ignored.

If you do need the component to stay synchronized with the prop, you should avoid storing it in state entirely and just use the prop directly inside your render logic, or compute it on the fly.

11. What are hooks in React and how to use them?

Section titled “11. What are hooks in React and how to use them?”

Hooks are built-in functions in React that allow you use state and different other React features inside functional components. Before Hooks, developers had to write class components to manage a component’s lifecycle or local state. Hooks let you “hook into” these capabilities using simpler, cleaner JavaScript functions.

You can either use built-in hook or combine them to build your custom hook.

Some of the built-in hooks are useState, useEffect, useMemo, useCallback etc.

Simple custom hook using react

Rules of Hooks

To ensure React can correctly track your state and lifecycle triggers, all Hooks must follow two main rules:

  1. Call Hooks only at the top level: Do not call Hooks inside loops, conditions, or nested functions.
  2. Call Hooks only from React functions: You can call them from React functional components or your own custom Hooks, but never from regular JavaScript functions or old class components.

12. What is useRef hook in React?

Section titled “12. What is useRef hook in React?”

The useRef hook is a built-in React hook that allows you to reference a value that is not needed for rendering. It returns a mutable object with a single property called .current.

Unlike state useState, mutating the .current property does not trigger a component re-render. The value you store inside a ref persists across your component’s entire lifecycle.

Core Use Cases

  1. Manipulating the DOM Directly

    The most common use case for useRef is to interact with HTML elements directly (similar to using document.querySelector in vanilla JavaScript). This is ideal for managing text input focus, scrolling to a specific element, or measuring element dimensions.

  2. Storing Information That Doesn’t Change the UI

    If a value needs to be remembered between renders but changing it shouldn’t cause the page to redraw, use a ref. Common examples include storing interval/timeout IDs, tracking a render counter, or caching previous state values.

13. What is the useId hook and when should it be used?

Section titled “13. What is the useId hook and when should it be used?”

The useId hook is a built-in React hook introduced in React 18 that generates unique, stable ID strings.

Its primary purpose is to create component-scoped identifiers that remain perfectly consistent across both the server and the client. This consistency solves a major problem in modern web apps: when using server-side rendering (SSR), functions like Math.random() or simple global counters will generate different IDs on the server than they do on the client, which completely breaks hydration. useId guarantees the exact same IDs are generated during both phases.

When to use useId?

You should use useId when you need to link DOM elements together for HTML accessibility attributes (ARIA). The most common use cases include:

  • Form Labels: Linking a
  • ARIA Attributes: Connecting descriptive elements with attributes like aria-describedby, aria-labelledby, or aria-controls.

When you build a reusable component that might be rendered multiple times on the same page, useId ensures that each instance gets its own unique ID pairs, preventing browser focus or screen reader clashes

When not to use useId?

Developers often mistake useId as a general-purpose unique string generator. There are strict scenarios where you must avoid it.

  1. Do not use it to generate keys in a list: React key props must be generated from your actual data (like a database ID). Using useId in a loop will break React’s reconciliation engine during re-renders.
  2. Do not use it as a data cache key: It should not be used to generate keys for caching systems or the use() hook.
  3. Do not call it conditionally or inside loops: Like all React hooks, useId must only be called at the very top level of your functional component.

14. How do you implement routing in React?

Section titled “14. How do you implement routing in React?”

We can implement routing in React using the React Router(react-router-dom) library. The modern, recommended approach (React Router v6.4+) uses a Data Router configuration, which separates route definitions from the JSX tree to enable advanced data-fetching APIs. Alternatively, you can use the traditional JSX component-based declaration.

  1. Approach A: The Modern Data Router

    This approach defines your routes as a JavaScript configuration array and provides them to the app using RouterProvider.

  2. Approach B: Traditional JSX Component Routing

    If you prefer configuring your routes directly inside your JSX component layout (e.g., inside App.jsx), wrap your layout with BrowserRouter.

16. What is the difference between useEffect and useLayoutEffect in React?

Section titled “16. What is the difference between useEffect and useLayoutEffect in React?”

The primary difference between useEffect and useLayoutEffect is when they execute in relation to the browser painting the screen. While both hooks share the exact same syntax and accept the same dependency arrays, they serve different performance and visual purposes.

  • useEffect runs asynchronously after the browser paints the screen. It non-blocking and won’t delay screen rendering. Primarily used for data fetching, event listeners and analytics.
  • useLayoutEffect runs synchronously before the browser paints the screen. It blocks painting until the code finishes executing. Primarily used for measuring DOM nodes, custom animations, fixing UI flickering.

17. What are Pure Components?

Section titled “17. What are Pure Components?”

A pure component in React is a component that renders the same output for the same state and props, helping optimize performance by skipping unnecessary re-renders.

They compare primitive values (like strings and numbers) by value, and complex values (like arrays and objects) by memory reference. If the shallow comparison finds no changes in props or state, React bypasses the render process entirely for that component. You can implement pure components depending on whether you are writing class-based or modern functional code.

Common Pitfalls:

  • Because pure components only do a shallow check, mutating a nested object or array directly in memory will fail to trigger a re-render. You must create a new copy of the object or array instead.
  • Passing objects created inline on each render breaks purity because a new reference is generated every time.
  • Inline Functions: Passing inline functions creates a new function instance on every render. Use the useCallback hook to preserve function references across renders.
  • The render phase must remain free of side effects and be completely predictable for identical inputs. The component must not use any guest/global variables that may cause unpredictable results.

18. What is the use of useCallback hook?

Section titled “18. What is the use of useCallback hook?”

useCallback is a React Hook that caches (memoizes) a function definition between re-renders.

When a React component re-renders, every function defined inside it is recreated from scratch. In most cases, this creation is fast and negligible. However, useCallback allows you to preserve the same function instance across renders unless its dependencies change.

On the initial render, useCallback returns the function you passed. On subsequent renders, if the dependencies haven’t changed, React returns the exact same function instance from the previous render.

When Should You Use It?

  1. Passing Callbacks to Optimized Child Components(Pure Components)

    If a child component is wrapped in React.memo to skip re-rendering when props don’t change, passing an inline function as a prop breaks that optimization—because a new function instance is created on every parent render.

  2. The Function is a Dependency in Another Hook If a function defined inside your component is listed in the dependency array of a useEffect, wrapping it in useCallback prevents the effect from firing on every single render.

  3. Custom Hooks

    When building custom hooks, any functions returned by the hook should generally be wrapped in useCallback so consumers can safely use them inside their own useEffect dependency arrays or optimized components.

19. What is the use of useMemo hook in React?

Section titled “19. What is the use of useMemo hook in React?”

useMemo is a React Hook that caches (memoizes) the calculated result of a function between re-renders, preventing expensive, resource-heavy calculations from running on every render.

  1. Skipping Expensive Recalculations

    React re-runs the entire component body whenever state or props change. If your component contains a heavy calculation, that calculation will execute again on every single render—even if the inputs to that calculation haven’t changed. useMemo wraps your calculation and only re-executes it when one of its specified dependencies changes.

  2. Preserving Referential Equality for Child Components

    In JavaScript, object and array literals ({}, []) are created with a new memory reference on every render. If you pass an unmemoized object or array as a prop to a child component wrapped in React.memo, the child will re-render every time because its prop reference changed.

  3. Stabilizing Dependencies for Other Hooks

    If an object, array, or computed value is included in the dependency array of another hook (like useEffect or useCallback), wrapping that value in useMemo prevents the dependent hook from firing unnecessarily on every render.

20. What is the use of useReducer hook in React?

Section titled “20. What is the use of useReducer hook in React?”

The useReducer hook in React is an alternative to useState designed for managing complex or multi-step state logic within a component. It follows the Redux-style state management pattern, taking a state and an action, and returning a new state.

  1. reducer(state, action): A pure function that takes the current state and an action object, and returns the next state based on the action type.
  2. initialState: The initial value of your state.
  3. dispatch(action): A function used to trigger state updates by passing an action object (typically containing a type string and optional payload).

Ideal Use Cases for useReducer

  • Complex Forms: Managing forms with multiple inputs, validation states, touched/dirty flags, and submission states.
  • Dependent State Updates: When the next state relies heavily on values in previous states or multiple fields need to update simultaneously (e.g., setting isLoading: true, error: null, and data: null on a fetch request).
  • State Machines: Modeling finite states (e.g., idle -> loading -> success / error) to prevent illegal state combinations.
  • Prop Drilling Mitigation with Context: Passing down a single static dispatch function via React Context to deep child components instead of creating and passing down multiple separate callback functions.

21. What is use of forwardRef() in React?

Section titled “21. What is use of forwardRef() in React?”

In React, forwardRef() is a utility function used to pass a ref through a component to one of its child components or to an underlying DOM element.

Key Use Cases

  • Direct DOM Access: Giving a parent component direct access to a child’s DOM node (e.g., to focus an input, scroll an element into view, or measure dimensions).
  • Higher-Order Components (HOCs): Forwarding refs through wrapper or container components so the consumer can access the wrapped component’s underlying DOM element or instance.
  • Component Libraries: Creating reusable, foundational UI elements (like buttons, inputs, or modals) that allow consumers to attach standard DOM refs.

In React 19, ref is a regular prop on function components and forwardRef is deprecated.

22. What is strict mode in React?

Section titled “22. What is strict mode in React?”

React Strict Mode (<React.StrictMode>) is a feature tool that wraps components to perform runtime checks and surface potential bugs during local development. It renders no visible UI and has zero impact on the production build.

Key Benefits:

  1. Detecting Impure Renders (Double Rendering)

    React expects component rendering to be a pure calculation with no side effects. In development mode, Strict Mode intentionally calls component functions and state updaters twice to surface unexpected side effects.

    If a component mutates an external variable during rendering, rendering it twice produces inconsistent results. Strict Mode exposes these side effects early before they cause subtle bugs in production.

  2. Validating Effect Cleanup (Double Effect Execution)

    In React 18+, Strict Mode mounts, unmounts, and remounts components on initial render in development.

    If a useEffect sets up a subscription, timer, or EventListener without returning a cleanup function, remounting leads to memory leaks or duplicate listeners. It immediately exposes missing cleanup logic (e.g., duplicate WebSocket connections or double API calls in dev mode).

  3. Detecting Deprecated or Unsafe APIs

    Strict Mode warns in the browser console when your app or third-party dependencies use outdated React patterns, including:

    • Unsafe Lifecycle Methods: componentWillMount, componentWillReceiveProps, componentWillUpdate
    • String Ref API: Using this.refs.myInput instead of useRef() or createRef().
    • Legacy Context API: Older context patterns replaced by React.createContext
    • Deprecated findDOMNode: An old escape hatch that breaks abstraction boundaries.

23. What are render props in React?

Section titled “23. What are render props in React?”

Render props is a technique in React for sharing code between components using a prop whose value is a function.

Instead of hardcoding what a component renders, the component accepts a function that returns a React element and calls that function inside its render logic.

Key Benefits

  • Code Reuse: Share complex behavior (like tracking scroll, handling form state, or fetching data) across multiple components without duplicating code.
  • Inversion of Control: The consumer determines how the UI looks based on the provided state, while the provider component handles how the state updates.
  • Dynamic Rendering: You can pass dynamic data into the callback function to render completely different UI structures in different contexts.

While render props were the standard solution for sharing stateful logic prior to React 16.8, Custom React Hooks have largely replaced them for most use cases because Hooks avoid deep JSX nesting (“wrapper hell”).

24. How do you prevent http request race conditions in React?

Section titled “24. How do you prevent http request race conditions in React?”

In React, we can use AbortController to cancel ongoing asynchronous tasks, most commonly fetch requests, when a component unmounts or when a user triggers a new request before the previous one finishes. This prevents memory leaks, race conditions, and unnecessary network bandwidth consumption.

25. What is reconciliation?

Section titled “25. What is reconciliation?”

Reconciliation is React’s process for determining what changed in your UI after a component re-renders, then applying only the necessary updates to the actual DOM. React compares the newly returned element tree with the previous one during the render phase, and applies the calculated changes during the commit phase.

For example:

When count changes:

  • React calls the component again and creates a new UI description.
  • React compares it with the previous description.
  • It notices that only the text inside <h1> changed.
  • React updates that text in the DOM instead of rebuilding the entire page.

What React compares?

React mainly uses these factors to decide whether to preserve or replace an element:

  • Element type: <div> and <span> are different types, so React replaces one with the other.
  • Position: Elements in the same position are generally compared with each other.
  • Props: If the type is unchanged, React updates changed props while reusing the existing DOM node.
  • Keys: In lists, keys help React identify which item was added, removed, or moved. Matching keys allow React to preserve the item’s state.

Example:

Use a stable, unique identifier such as item.id, rather than an array index when list items can be reordered or removed.

26. What is code splitting in React?

Section titled “26. What is code splitting in React?”

Code splitting in React is the practice of dividing your application’s JavaScript bundle into smaller chunks that are downloaded only when needed. Instead of loading the entire app at startup, the browser loads the code required for the current page and fetches other features later. This can reduce initial load time and improve responsiveness.

React commonly uses JavaScript’s dynamic import() together with React.lazy and Suspense.

Example:

Here:

  • SettingsPage is placed in a separate JavaScript chunk by the bundler.
  • That chunk is downloaded when React needs to render the component.
  • Suspense displays a fallback while the chunk loads.

Benefits and trade-offs

Benefits:

  • Smaller initial JavaScript download.
  • Faster startup, especially for large applications.
  • Less JavaScript to parse and execute initially.
  • Heavy features or rarely used pages can load on demand.

Trade-off: each additional chunk may require a network request, so splitting extremely small components can add unnecessary overhead. In practice, split at route boundaries or around large, optional features.

27. What’s new in React 19?

    • Error handling through Error Boundaries.
    • Automatic optimistic-update rollback.
    • Functions passed directly to <form action> and formAction.
    • Automatic resetting of uncontrolled forms after successful submission.

28. What is React Fiber?

Section titled “28. What is React Fiber?”

React Fiber is React’s internal reconciliation architecture system that React uses to determine what changed in your component tree and how to update the UI efficiently and incrementally. It was introduced in React 16 as a rewrite of the older stack-based reconciler.

How it works

React represents each component or rendered element with a Fiber node. A Fiber stores information such as:

  • The component or DOM element type.
  • Its props and state.
  • Its position in the component tree.
  • Its relationship to parent, child, and sibling Fibers.
  • Work that React needs to perform for that node.

React breaks rendering into smaller units of work instead of processing the entire tree in one uninterrupted call stack. This allows it to:

  • Pause and resume rendering.
  • Split large updates into chunks.
  • Prioritize urgent updates.
  • Reuse completed work.
  • Abandon work that is no longer needed.

Render and commit phases

Fiber separates an update into two broad phases:

  • Render phase: React calculates what should change. This work can be interrupted or restarted.
  • Commit phase: React applies the completed changes to the DOM. This phase is kept consistent and is not partially applied.

For example, while React is rendering a large list, a more urgent input update can receive priority so typing remains responsive.

Tip

The old reconciler was like completing one long task without interruption. Fiber turns that task into smaller jobs that React can schedule, pause, prioritize, or discard.

29. How would you investigate a React page that feels slow?

Section titled “29. How would you investigate a React page that feels slow?”

Investigating performance issues in a React application requires a systematic approach to isolate whether the bottleneck is caused by rendering overhead, unnecessary re-renders, network/data fetching latency, or main-thread blocking JavaScript.

Here is a structured framework for diagnosing and fixing a slow React page.

  1. Initial Profiling & Measurement
    Before writing or changing any code, establish baseline metrics to pinpoint where time is being spent.

    A. Chrome DevTools (Performance Tab)

    1. Open DevTools in an Incognito Window (to disable extensions that distort performance).
    2. Record a Performance Profile while interacting with the slow feature.
    3. Check the Main Thread Flamechart:
      • Long Tasks (Red Flags): Tasks taking longer than 50ms block user input.
      • Call Stack: Look for heavy JavaScript execution, excessive layout thrashing, or expensive synchronous calculations.
    4. Check Core Web Vitals:
      • LCP (Largest Contentful Paint): Indicates slow initial loading or unoptimized images/assets.
      • INP (Interaction to Next Paint): Indicates slow response to clicks, taps, or keypresses.
      • CLS (Cumulative Layout Shift): Highlights layout instability during load or state updates.

    B. React Developer Tools Profiler

    1. Install the React DevTools extension.
    2. Open the Profiler tab and check “Record why each component rendered during profiling” in settings.
    3. Start recording, perform the slow interaction, and stop.
    4. Analyze the Flamegraph and Ranked Chart:
      • Yellow/Orange bars: Components that took a long time to commit.
      • Render Reasons: Hover over components to see why they rendered (e.g., “Props changed”, “Parent component rendered”, “Hook 3 changed”).

  2. Identify the Root Cause
    Once you have gathered profiler data, categorize the issue into one of four primary buckets:

    • Excessive/Un-necessary Render
      • Cascading renders
      • Inline reference churn
      • Unsplit Context state
    • Heavy Component Tree & DOM
      • Large lists (>100 items)
      • Heavy sync calculations
      • Heavy layout / CSS recalculations
    • Bundle Size & Loading Bottlenecks
      • Large resources like images, fonts etc.
      • Large bundle instead of multiple small bundles.
      • Unoptimized bundles
      • Heavy library imports
    • Network & Data Fetching
      • Waterfall API calls
      • Uncached requests

  3. Targeted Fix Strategies

    • Bucket A: Excessive or Unnecessary Re-Renders

      • Context Splitting: If using React Context, ensure frequently changing state is separated from static context. A single context change forces every consumer component to re-render.
      • State Colocation: Push state down as close as possible to where it is actually consumed rather than keeping it high in the component tree.
      • Stable References:
      • Wrap expensive sub-trees or pure presentational components in React.memo.
      • Pass stable callbacks using useCallback and memoize derived prop values using useMemo when passing them down to memoized children.
      • Render Diagnostics: Use tools like why-did-you-render in development environments to log unnecessary re-renders automatically to the console.

    • Bucket B: Heavy Main Thread & DOM Operations

      • List Virtualization: For rendering large datasets (hundreds or thousands of DOM nodes), implement windowing/virtualization using libraries like react-window or @tanstack/react-virtual.
      • Defer Non-Critical Updates:
      • Use useTransition to mark non-urgent state transitions (e.g., filtering a long list while typing in a search bar), keeping input typing responsive.
      • Use useDeferredValue for values that update too frequently.
      • Offload Heavy Calculations: Move complex synchronous computations (data transformations, sorting) out of the render loop into Web Workers using comlink or memoize them with useMemo.

    • Bucket C: Bundle Size & Loading Bottlenecks

      • Route & Component Code Splitting: Use React.lazy() and Suspense or framework-level dynamic imports (e.g., Next.js dynamic()) to split code by route or non-critical modal/tab component.
      • Analyze Bundle Dependencies: Use source-map-explorer or webpack-bundle-analyzer to identify large packages (e.g., full lodash imports, heavy date/charting libraries) and swap them for lighter alternatives or tree-shakeable imports.
      • Asset Optimization: Ensure images are lazily loaded, modern formats (.webp, .avif) are served, and fonts are preloaded.

    • Bucket D: Data Fetching Latency

      • Eliminate API Waterfalls: Shift sequential useEffect fetches into parallel requests or move data fetching to the server level (Server Components / SSR loaders).
      • Client Caching & Stale-While-Revalidate: Use structured data-fetching solutions like @tanstack/react-query or SWR to handle caching, background updating, and optimistic UI updates.

  4. Verification & Prevention\

    1. Re-profile: Compare production-build performance traces before and after changes to verify measurable improvement (aim for lower Total Blocking Time and improved INP).
    2. Automate with Lighthouse / CI: Add Lighthouse CI checks to pull requests to prevent performance regressions on critical user journeys.
    3. Field Data Monitoring: Integrate Real User Monitoring (RUM) tools like Sentry, Datadog, or Vercel Analytics to track production Core Web Vitals (INP, LCP, CLS) across diverse device types and network conditions.

31. What is hydration and hydration mismatch in React?

Section titled “31. What is hydration and hydration mismatch in React?”

What is hydration in React?

Hydration is the process by which React converts server-rendered (or statically pre-rendered) HTML into a fully interactive client side application by attaching event handlers and initializing state without recreating the existing DOM nodes.

In a typical Server-Side Rendering (SSR) setup:

  • The server renders your React components to HTML and sends that HTML to the browser.
  • The browser displays this HTML immediately, so the user sees content quickly.
  • Once the JavaScript bundle loads, React “hydrates” that HTML. It walks the existing DOM tree, matches it against your component tree, and attaches event listeners and state.

Think of the server HTML as a “dry” skeleton, hydration is React pouring in the “water” of interactivity (events, state, effects) so the page becomes alive.

Hydration Mismatch

A hydration mismatch (or hydration error) happens when the HTML that React generates on the client during its first render does not exactly match the HTML that was rendered on the server.

Because hydration assumes the two trees are identical, any difference means React cannot safely reuse the server DOM as-is. When a mismatch is detected, React:

  • Logs a warning/error showing the difference.
  • Discards the mismatched part of the server-rendered tree (from the nearest Suspense boundary downward).
  • Re-renders that part from scratch on the client.

This can cause visible issues like:

  • Content flickering or shifting after load.
  • Event handlers not working until after re-render.
  • Inconsistent UI between initial paint and interactive state.

Common causes of hydration mismatches

Typical reasons the server and client renders differ include:

  • Using browser-only APIs during render
    Accessing window, localStorage, document, or similar in code that runs on the server (e.g., in Next.js Server Components or during SSR) will produce different output on server vs client.

  • Non-deterministic rendering
    Using Math.random(), Date.now(), or other values that change between server and client renders leads to different HTML.

  • Conditional rendering based on environment
    Rendering different content depending on whether code is running on the server or client (e.g., typeof window === 'undefined' checks that change the rendered JSX).

  • HTML structure differences
    Invalid HTML nesting (e.g., <div> inside <p>) that the browser auto-corrects differently than React expects can also trigger mismatches.

How to avoid or fix hydration mismatches

Common strategies:

  • Move browser-only logic to effects or client components
    In frameworks like Next.js, put code that uses window, localStorage, etc. inside useEffect or mark the component with "use client" so it only runs in the browser.

  • Ensure render output is deterministic
    Avoid random values or timestamps in the rendered markup unless they’re generated in a way that’s consistent between server and client (or deferred to after hydration).

  • Use suppressHydrationWarning carefully
    For known, safe one-off differences (like a timestamp that only affects text content), React allows suppressHydrationWarning on specific elements, but this should be used sparingly and only when you understand the risk.

  • Check component boundaries
    Make sure Server Components and Client Components are separated correctly and that anything needing browser APIs is not rendered during the server pass.

33. Explain different types of rendering mechanism in React and their use?

Section titled “33. Explain different types of rendering mechanism in React and their use?”

React applications support several rendering strategies, each suited to different performance, SEO, and interactive needs.

Mechanism Description Render Location Ideal Use Cases
CSR (Client-Side Rendering) HTML skeleton sent; browser downloads JS bundle to render content. Browser Internal dashboards, gated SaaS platforms, highly dynamic interactive apps.
SSR (Server-Side Rendering) HTML generated on the server per user request with dynamic data. Server (on request) E-commerce product pages, news feeds, content requiring personalized SEO.
SSG (Static Site Generation) HTML generated at build time and cached globally on a CDN. Server (at build time) Documentation sites, blogs, marketing landing pages, help centers.
ISR (Incremental Static Regeneration) Rebuilds individual static pages in the background without a full rebuild. Server (on background revalidation) Large-scale content platforms, broad e-commerce catalogs, news portals.
RSC (React Server Components) Components execute on the server and stream UI primitives without shipping JS. Server (streaming to client) Modern full-stack React applications (e.g., Next.js App Router).

Deep Dive into Each Strategy

  1. Client-Side Rendering (CSR)

    In traditional CSR apps (like classic Create React App or Vite React setups), the server serves a bare HTML shell containing a script tag. The browser downloads the Javascript, executes React, pulls data via API calls, and updates the DOM.

    • Pros: Smooth page transitions after initial load, reduced server execution burden (handled by the client).
    • Cons: Slower initial page load (First Contentful Paint), poor SEO default performance without workarounds.
    • Best Used For: Private dashboards, account settings, or apps where SEO is unnecessary and user interaction dominates.

  2. Server-Side Rendering (SSR)

    With SSR (supported by frameworks like Next.js and Remix), every incoming HTTP request causes the server to execute React, fetch fresh data, and compile the full HTML markup before sending it to the browser. The browser then hydrates the HTML to attach event listeners.

    • Pros: Excellent for real-time SEO, fast First Contentful Paint (FCP), guaranteed fresh data on every request.
    • Cons: Higher server load/costs, potential delay in Time to First Byte (TTFB) while waiting for server data fetching.
    • Best Used For: Highly dynamic public pages like live inventory views, personalized user feeds, or personalized dashboards needing SEO.

  3. Static Site Generation (SSG)

    SSG builds every single route into flat HTML and JSON files during the continuous integration / build step. These pre-built files are deployed directly to a Content Delivery Network (CDN) edge.

    • Pros: Blazing fast load times, minimal server costs, maximum reliability under high traffic spikes.
    • Cons: Long build times for large sites; content remains stale until a new build and deployment occur.
    • Best Used For: Marketing sites, blogs, portfolios, documentation hubs, and privacy policies.

  4. Incremental Static Regeneration (ISR)

    Popularized by Next.js, ISR combines SSG with dynamic cache revalidation. Pages are generated statically at build time, but when a revalidation interval expires (e.g., revalidate: 60), the next incoming request triggers a background regeneration without blocking the user.

    • Pros: Fast CDN speeds like SSG, but with scalable updates without redeploying the entire website.
    • Cons: First visitor after cache expiration gets stale content while the background rebuild executes; non-trivial state consistency across distributed deployments.
    • Best Used For: E-commerce sites with thousands of products, news archives, and large multi-author publication platforms.

    Read more

  5. Streaming SSR and Partial Hydration (advanced)

    • Streaming SSR:
      The server streams HTML chunks to the client as they’re ready, instead of waiting for the entire page to render. This improves perceived load time, especially for large pages.

    • Partial hydration / Islands architecture:
      Only certain interactive “islands” of the page are hydrated with JavaScript; the rest remains static HTML. This reduces JS cost and improves performance.

  6. React Server Components (RSC)

    RSC splits component rendering at the architecture level. Server Components run exclusively on the server can directly query databases or access secrets and send serialized UI data to the browser with zero added JavaScript bundle size. Client Components handle traditional interactive state (useState, useEffect).

    • Pros: Significantly smaller JavaScript bundles, fast rendering pipeline, direct access to backend resources directly inside the component tree.
    • Cons: Requires specialized framework routing (e.g., Next.js App Router, Waku), stricter mental model around server/client boundaries.
    • Best Used For: Modern full-stack React projects seeking optimal performance alongside server-side resource fetching.

Tip

SSR vs RSC:

  • SSR is a page-level strategy that converts an entire component tree into HTML. RSC is a component-level architecture where individual components run on the server.
  • SSR requires client-side hydration (downloading and running JavaScript for all components on the browser) to make the page interactive. RSC components have zero hydration because their code never ships to the browser.
  • SSR sends raw HTML to the browser. RSC sends a special serialized payload describing the rendered component tree, which seamlessly merges with client components.
  • SSR components can use standard React state and hooks after hydration. Pure RSC server components cannot use hooks like useState or browser APIs because they never execute in the browser.

35. How would you solve data fetching waterfall across nested components?

Section titled “35. How would you solve data fetching waterfall across nested components?”

A data fetching waterfall occurs when nested components trigger network requests sequentially rather than in parallel. Meaning Child B cannot start fetching its data until Parent A finishes fetching its data and renders.

Key Strategies to Eliminate Waterfalls

  1. Parallelize at the Route / Server Level (Server Components / Framework Loaders)

    If you are using modern React (Next.js App Router, Remix, or React Server Components), move data fetching to the server level or route level.

    • React Server Components (RSC): Fetch data in parallel on the server using Promise.all().
    • Route Loaders (Remix / React Router 6.4+): Execute route-level loaders concurrently before components start rendering.

  2. Component-Level Preloading (Data Preloading Patterns)

    If data fetching must stay on the client (e.g., standard Client-Side Rendering with useEffect or React Query), trigger the network request before or as soon as the parent starts loading, rather than waiting for child components to mount.

  3. Render-as-You-Fetch with React Suspense

    Instead of Fetch-on-Render (fetching in useEffect after mount), adopt Render-as-You-Fetch. Fire requests immediately upon interaction or route change, then pass the pending promise to <Suspense>.

    • Suspense boundaries allow sibling or nested trees to render up to the boundary without blocking the whole UI.
    • React starts fetching data and rendering the component tree concurrently.

  4. GraphQL / Relay Fragment Colocation

    If using GraphQL, components define their data requirements via fragments, but the root route compiles these fragments into a single GraphQL query.

Summary

Strategy Ideal Use Case Pros
Server Components / Route Loaders Next.js, Remix, SSR apps Solves waterfalls completely with 0 client JS overhead.
Promise.all / Parallel Fetching Single component needing multiple resources Simple, straightforward JavaScript.
Prefetching / React Query Single-Page Apps (CSR) Keeps component-level encapsulation without layout blocking.
GraphQL Fragments (Relay) Complex, deeply nested component trees Solves waterfall while preserving component-data colocation.

36. What are the cons of using React context?

Section titled “36. What are the cons of using React context?”

While React Context is a great built-in solution for passing global data through a component tree without manually passing props at every level, it introduces several trade-offs when overused or applied to the wrong use cases.

Core Disadvantages & Drawbacks

  • Performance & Re-render Issues Every component consuming a context will automatically re-render whenever the context value object changes—even if that component only uses a small property of the state that didn’t change. Unlike dedicated state management libraries (like Zustand or Redux Toolkit), Context lacks fine-grained selectors out of the box.
  • Architectural & Component Coupling Components that rely directly on context become tightly coupled to that specific provider hierarchy. This makes them significantly harder to reuse elsewhere in your application, isolate in component libraries, or render independently in unit tests without wrapping them in context mock providers.
  • Provider Nesting (“Provider Hell”) As an application grows, storing different slices of state (theme, auth, user settings, notifications, feature flags) in separate contexts can result in deeply nested component trees in your root component (<AuthProvider><ThemeProvider><SettingsProvider>...).
  • Lack of DevTools & Debugging Support Unlike Redux, React Context doesn’t offer built-in action logging, state travel/time travel, or clear state diffs. Debugging where a state change originated or tracking complex state updates across multiple providers can quickly become difficult.
  • Poor Suitability for High-Frequency State Context is designed for low-frequency updates (like theme changes, current user data, or UI locale). It is inefficient for fast, high-frequency updates—such as mouse position tracking, complex form inputs, or rapid real-time updates—due to the cascade of re-renders.

When to Use Context vs. Alternatives

Feature / Use Case React Context External State Management (Zustand, Redux)
Best For Low-frequency, app-wide values (Theme, Auth, Locale) Complex, high-frequency, or deeply nested state
Re-render Optimization Coarse (Re-renders all consumers) Fine-grained (Selector-based subscriptions)
Setup Complexity Very Low (Native to React) Low to Moderate
Testing Isolation Requires Provider wrappers Easy to mock store state directly

  1. Caching Static Assets (Build Files)

    The index.html file must never be aggressively cached. It references bundled JS and CSS assets using content hashes (e.g., main.a8f92c.js). If a browser caches index.html, users won’t receive app updates until their local cache expires.

    Header for index.html:

    • no-cache: Tells the browser to validate with the server before using a cached copy.
    • no-store: Prevents storing the HTML file anywhere (optional, but ensures complete cache bypass).

    Modern bundlers append unique hash strings to filenames whenever code changes. Since a filename change guarantees fresh content, these files can be cached safely for up to a year (the maximum allowed by HTTP specs).

    Header for fingerprinted assets:

    • max-age=31536000: Caches the file for 1 year ($365 \times 24 \times 60 \times 60$ seconds).
    • immutable: Tells the browser the file content will never change, preventing conditional revalidation requests (304 Not Modified) on page reloads.
